# HIS 对接 · 联调前需当面定死的三件事

> MediScribe 项目组 · 2026 年 9 月 1 日
> 建议在联调启动会上逐条确认，并把结论写回接口规范。

我方在联调前做了一轮"站在贵方位置上"的复核，发现三处**联调当天不会暴露、但上线一周内必然出问题**的地方。这三条都不是代码 bug，而是双方约定没定死或规范表述与实现不一致，必须当面确认。

另附一份联调当天的自查清单。

---

## 一、`record.*` 结构化字段回写的是问诊表单内容，不是医生签发的最终病历

### 现状

规范 3.2 写的是：

> `record.*` 为结构化字段，**供 HIS 逐字段回填病历**；`full_text` 为病历完整文本（医生最终签发版），供 HIS 存档、或在无法逐字段映射时整体落库——二者一并下发。

按这个描述，贵方的首选落库路径是逐字段回填 `record.*`。

但我方实现里，`record.*` 的 23 个字段全部取自**问诊表单**，而医生在病历编辑器里做的最终修改只进 `full_text`。两者在医生改过病历之后就不一致了。

### 为什么联调当天发现不了

联调用测试数据走一遍，通常是"AI 生成 → 直接签发"，中间不修改，此时 `record.*` 与 `full_text` 内容一致，怎么比对都是对的。

而生产上医生**天天都在改**。改完之后，贵方按规范首选路径回填进法定病案的，是医生修改之前的版本。

### 另有 6 个字段结构性恒空

以下字段在我方系统里存放于**患者档案**（跨就诊的纵向数据），不在问诊表单里，因此永远不会出现在回写报文中：

| 字段 | 说明 |
|---|---|
| `past_history` | 既往史 |
| `allergy_history` | **过敏史** |
| `personal_history` | 个人史 |
| `current_medications` | 长期用药 |
| `family_history` | 家族史 |
| `marital_history` | 婚育史 |

贵方若已按规范 3.2 建好了这些列，会一直收不到值。**其中过敏史恒空是用药安全问题**，请特别注意。

### 需要确认

1. 贵方目前是按 `record.*` 逐字段回填，还是直接存 `full_text`？
2. 若按字段回填，我方需要调整为"签发时把最终内容回灌问诊表"，或改由 `full_text` 作为唯一权威。**这个改动方向请贵方给意见**——哪种对贵方落库更友好。
3. 上面 6 个字段：是贵方另行从我方患者档案接口取，还是我方把它们并入回写报文？

## 二、规范 v1.4 写着"不下发 code/code_type"，而我方已经在下发

### 现状

规范 v1.4 第 4 章原文：

> 我方以诊断名称（`name`）为准，**不下发 `code` / `code_type`**。

而当前实现已经在下发 `code`、`code_type`，另外还多了一个 v1.4 全文没有的 `admission_condition`（入院病情标志）。

这些是 2026-08-21 病案首页质控工程上线时加的，对应的《接口规范 v1.5 增补说明》已经写好，**但尚未发给贵方**。

### 风险

若贵方手上仍是 v1.4，最坏的情况不是忽略这个字段，而是**把我方下发的 `code` 当成贵院诊断字典的编码直接落库**。

我方下发的是国家医保 2.0 / GB-T 15657-2021 口径的编码，与贵院本地字典未必同源。错误编码进入病案首页会直接影响医保结算。

### 因此

**在收到并确认 v1.5 增补说明之前，请不要开始诊断编码相关的联调。** 我方会随本文档一并提供 v1.5。

## 三、回写重投可能覆盖医生已在 HIS 端确认保存的正式病历

### 现状

规范 2.5 目前的表述是：

> 回写仅作用于草稿/待确认病历；若该就诊病历已被医生确认为正式病历，HIS **可拒绝或按新版本处理（联调约定）**。

两种相反的做法都写在纸面上，至今没有定论。

而我方的对账机制会在以下情况重投同一份病历：**写入其实成功了、只是刷新消息没有收到回执**（`refresh_failed`）——这恰恰是最常见的一种情形，约 5 分钟后会重推一次。

### 两种选择的后果

| 贵方选择 | 后果 |
|---|---|
| 按新版本处理 | 医生在 HIS 端确认保存成正式病历后，我方重投会把它覆盖回草稿内容 |
| 拒绝 | 我方收到非 0 返回码，会一直标记为失败，重试 5 轮后触发告警邮件刷屏 |

**联调当天不会暴露**——当天没有人会在 HIS 端做"确认保存成正式病历"这个动作。上线一周内必现。

### 需要确认

1. 贵方选哪一种？
2. 若选"拒绝"，请约定一个**专用返回码**（而不是通用错误码），我方收到它就停止重投并标记为"HIS 侧已定稿"，不再告警。
3. 结论请写回规范 2.5，替换掉现在那句"可拒绝或按新版本处理"。

## 附：联调当天自查清单

以下几条是我方复核时发现的、容易在现场卡住的点，已在我方侧处理或说明，供贵方对照。

### 1. WebSocket 心跳（我方已调整，贵方无需改动）

我方服务端此前除规范 7.4 约定的**应用层 JSON 心跳**（我方每 30 秒下发 `type=ping`）外，还会发送 **RFC6455 协议层 PING 控制帧**（opcode `0x9`），20 秒收不到 PONG 就断连——这一条规范里没有写。

如果贵方客户端是自行解析 WebSocket 帧（Delphi / C# / Java 常见），只实现了文档里的 JSON ping/pong，现场表现会是"握手成功，每 40 秒左右被踢一次，没有任何错误码"。

**我方已关闭协议层心跳**，只保留规范写明的应用层心跳。贵方按规范实现即可。

### 2. 规范标"必填"的字段，我方目前不做强校验

规范 3.1 标注必填的字段中，我方实际强制的只有 `visit_id`、`hospital_code`。其余缺失时我方会降级处理并放行（这是有意的容错设计——绝不因脏数据拒收接诊）：

| 字段缺失 | 我方行为 |
|---|---|
| `gender` | 降级为"未知" |
| `birth_date` | 静默丢弃 |
| **`dept_code`** | **回落为该医生的编制科室** |
| `doctor_name` | 接收后不使用 |
| `patient_name` | 使用占位名"未知患者"（急诊无名氏场景） |

请特别注意 `dept_code`：如果贵方映射时漏了这个字段，**联调当天 ack 全部返回 0、患者也能正常进入医生工作台，没有任何人会发现**。但上线后所有接诊的科室都会落成医生的编制科室，同时污染病案首页科室、质控科室统计、复核队列过滤三处。

**建议贵方在联调时自行核对一次这几个字段确实发出去了。**

### 3. 幂等与重发

- 接诊推送幂等键：`hospital_code` + `visit_id`
- 消息去重键：`msg_id` + 报文内容指纹（10 分钟窗口）。**同一 `msg_id` 配不同内容会被当作新消息正常处理**，请勿把 `msg_id` 按 visit 生成或写死
- 超时重发请使用**相同的 `msg_id`**，我方按上述规则幂等
- 回写幂等键：`visit_id` + `record_type` + `record_no`（门急诊 `record_no` 恒为 `"1"`，住院递增）

### 4. 时间戳与签名

- 时间戳窗口 ±5 分钟，请确认贵方服务器已开启 NTP 对时
- 待签串：`app_id + timestamp + nonce + payload原文`，握手阶段 payload 段固定为字符串 `handshake`
- 我方验签**按贵方实际发送的字节**进行，不会重新序列化——贵方无需担心键序或空格差异
